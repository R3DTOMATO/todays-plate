# 피드·탈퇴·주변 검색 수정 — 2026-09-09

이 변경은 로그인 우선 흐름 PR #3 위에 쌓은 후속 수정이다. 운영 배포는 하지 않았다.

## 수정 결과

- 신규 게시물의 존재 여부 조회가 허용되지 않아 첫 공개가 실패하던 규칙을 수정했다. 로그인 사용자의 없는 문서 단건 조회만 추가 허용하며 비공개 글 조회·목록 권한은 넓히지 않았다.
- 좋아요 카운터와 사용자 좋아요 문서의 변경 전·후 상태를 함께 검증한다. 카운터만 증가하거나 좋아요 문서만 쓰는 요청을 거부한다. 화면의 내 좋아요 조회도 컬렉션 전체 대신 본인 문서 하나를 읽는다.
- 댓글·좋아요 접근은 부모 게시물의 공개 상태를 확인한다. 비공개/삭제 중 글은 타인에게 보이지 않는다. 이미 없는 부모의 하위 데이터에도 접근할 수 없다.
- 게시물 삭제는 `deleting` 상태로 새 상호작용을 막고, 좋아요·댓글 전체와 사진을 정리한 후 부모 문서를 삭제한다. 실패하면 부모를 보존해 내 식탁에서 재시도한다.
- 공개된 식사 기록을 다시 저장하면 메모·메뉴·만족도·사진 등도 갱신한다. 기존 좋아요·댓글 집계와 생성 시각은 유지한다. 공개 여부 조회 실패를 비공개 상태로 오인하지 않으며, 로컬 기록 저장은 가능하고 피드 변경은 보류한다.
- 주변 직접 검색에 이전 추천 메뉴의 업종 제한이나 음식 이미지를 사용하지 않는다. 거리 원본 숫자를 보존해 단위를 섞어 정렬하지 않는다. 외부 지도는 현재 검색어로 열며, 늦은 검색 응답이 새 결과를 덮어쓰지 않게 한다.

## 탈퇴 실패·재시도

Firestore 조회·삭제와 Storage HTTP 실패를 전파한다. 500개 조회 제한과 300개 하위 문서 페이지를 넘어도 대상이 소진될 때까지 처리한다. Storage의 다음 페이지 토큰도 처리한다. 남의 글에 남긴 좋아요 삭제와 카운터 감소는 문서 버전 전제조건을 둔 한 번의 원자적 commit으로 처리해 재시도 시 이중 감소·부모 재생성을 방지한다.

서버는 `accountDeletions/{uid}`에 최소 상태 `{active:true}`를 기록한다. 정리 중인 계정의 기존 세션이 Firestore 문서를 새로 쓰거나 Storage에 사진을 추가하지 못하게 한다. 중간 실패 후 로그인하면 탈퇴 재시도 화면으로 진입한다. 탈퇴는 일부 데이터부터 지우는 작업이므로 이 단계에서 취소·복원을 제공하지 않는다.

Auth 삭제는 마지막이다. 성공 후에도 이미 발급된 토큰의 재사용을 막기 위해 UID별 삭제 표식을 유지한다. 표식에는 이름·이메일·설문·사진을 넣지 않는다. 보존 기간/TTL을 도입하려면 기존 토큰 만료와 재가입 UID 정책을 확인해야 한다. 남의 글에 작성한 댓글은 기존 정책대로 본문을 남기고 작성자 ID·이름을 익명화한다. 그룹 투표의 과거 참여 기록 정리는 이번 수정 범위에 포함하지 않았다.

서버와 피드 변경 테스트는 API 경계를 대체한다. 브라우저는 Firebase/Kakao 응답을 대체한다. 에뮬레이터는 저장소의 실제 Firestore·Storage 규칙으로 허용·거부를 검증한다. 실제 OAuth·운영 IAM·운영 색인 준비·Kakao 검색 품질·운영 탈퇴 API의 종단간 검증은 남아 있다.

재현 명령:

```sh
npm run test:cleanup
# Firebase CLI, firebase, @firebase/rules-unit-testing가 개발 환경에 설치되어 있어야 한다.
npm run test:rules
# 다른 터미널에서 python -m http.server 9154 실행 후:
npm run test:entry
```

이번 에뮬레이터 검증은 firebase-tools 13.35.1, firebase 10.12.2, @firebase/rules-unit-testing 3.0.4, Java 17을 격리된 개발 도구 경로에 설치해 실행했다. 이 버전들은 운영 서버 의존성에 추가하지 않았다. 별도 설치 경로는 `PLATE_TEST_DEPS`로 지정할 수 있다.

## 운영 반영 순서와 남은 확인

1. 테스트 Firebase 프로젝트에 Firestore/Storage 규칙과 `firestore.indexes.json`을 함께 반영한다. Storage가 Firestore의 삭제 표식을 읽도록 필요한 서비스 간 권한을 승인·확인한다. 새 컬렉션 그룹 단일 필드 색인이 준비될 때까지 기다린다.
2. 서버에 기존 Admin 자격 증명과 정확한 `FIREBASE_STORAGE_BUCKET`이 있는지 확인한다. 버킷 미설정은 삭제 성공으로 처리하지 않는다.
3. 규칙·색인 준비 후 서버, 웹을 반영한다. 새 규칙은 기존 클라이언트의 게시물 직접 삭제를 막으므로 같은 배포 창에서 웹을 갱신한다.
4. 실제 이메일/Google/Apple 로그인, 사진 공개/수정/비공개/삭제, 삭제 실패 후 재로그인 복구, 탈퇴 API를 별도 테스트 계정으로 확인한다.
5. 과거에 이미 생성된 고아 하위 문서·사진과 잘못된 카운터는 자동 소급 정리하지 않았다. 운영 데이터 진단 후 별도 보정이 필요하다. 그룹 투표 기록의 탈퇴 정책도 후속 확정이 필요하다.

규칙의 원자적 쓰기 검증은 [Firebase 공식 문서의 getAfter 설명](https://firebase.google.com/docs/firestore/security/rules-conditions)을 참고했다. 이번 결과를 전체 서비스의 모든 오류가 해결됐다는 의미로 해석하지 않는다.
