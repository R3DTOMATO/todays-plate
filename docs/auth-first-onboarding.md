# 로그인 우선 입맛 추천 — 2026-09-08

## 사용자 흐름

1. 미로그인 사용자는 회원가입·로그인 화면으로 진입한다.
2. 첫 로그인에서는 음식 문화, 선호 음식 종류, 알레르기, 제외 재료, 식단 제한의 다섯 단계를 진행한다. 기존 6·7·8단계(포만감·평소 예산·평소 상황)는 제거했다.
3. 저장 성공 후 식사 방식 → 오늘의 상황 → 예산 세 질문으로 추천한다. 재로그인에서는 저장된 설문을 복원한다.
4. 결과는 기존 대표 메뉴 하나와 대안 두 개 구조를 유지한다. 후보가 부족하면 제한을 자동으로 풀지 않는다.

입맛 수정은 프로필에서 가능하다. 설문 저장 실패 시 선택을 유지하고 재시도할 수 있다. 저장 완료 전에는 최초 추천을 시작하지 않는다. 계정 변경 시 늦게 도착한 이전 계정 응답을 무시한다.

## 저장 및 데이터

- 다섯 설문 답과 완료 버전은 `users/{uid}/private/taste`에 저장한다. 공개 사용자 프로필과 분리하며 본인만 접근하는 Firestore 규칙을 추가했다.
- 설문과 로컬 학습 프로필의 캐시는 UID별로 나눈다. 기존 게스트 설문을 새 계정에 자동 귀속시키지 않는다.
- 식사 기록·찜은 기존 기기 저장 방식을 유지한다. 모든 사용자 데이터의 계정별 동기화를 구현한 것은 아니다.
- 탈퇴 서버는 신규 비공개 입맛 문서를 삭제해야 다음 사용자 문서 삭제로 진행한다.
- 레시피 재료 로딩 후 알레르기 태그를 생성하도록 순서를 수정했다. 태그는 여전히 키워드 추론이므로 재료 누락·교차 오염 여부까지 보장하지 않는다.

## 직접 요리와 추천 점수

직접 요리는 레시피가 있고 예상 시간이 30분 이내이며 기존 집밥 적합성 기준을 통과하는 메뉴부터 추천한다. 결과 화면에서 사용자가 모든 레시피로 범위를 넓힐 수 있다. 족발처럼 시간이 걸리는 요리도 포함할 수 있다. 족발 레시피 시간은 단계별 소요 시간에 맞춰 125~155분으로 수정했다.

점수제는 유지한다. 설문 선호는 순위에 반영하고 알레르기·제외 재료는 후보 제외에 사용한다. 예산 보너스는 이번 선택 금액을 사용하며, 초과 후보는 표시한다. 검증되지 않은 적합도 백분율을 제거하고 추천 이유를 제시한다.

로그인과 질문 축소만으로 추천 정확도가 입증되지는 않는다. 후속 실험은 추천 후 선택률, 실제 식사 기록 전환율, 재추천·거절률, 추천 종류의 다양성을 함께 측정해야 한다. 사용자별 반복 노출을 고려해 현 점수와 변경 점수를 비교한 뒤 가중치를 조정한다. 메뉴 수 확장은 별도 후속 작업이다.

## 검증

- 브라우저: `scripts/test-entry-flow.py`의 25개 검증 통과. 로그인 게이트, 다섯 설문, 저장 실패 재시도, 세 질문, 연속 클릭, 재료 필터, 직접 요리 범위, 예산 초과 설명, 계정 분리·응답 순서, 320/393/768px 넘침 및 페이지 오류를 확인했다.
- 테스트는 Firebase Auth와 Firestore 응답을 대체하며 실제 계정을 만들거나 운영 데이터를 쓰지 않는다. 실제 OAuth, 배포된 보안 규칙, 탈퇴 API는 이 테스트의 검증 범위가 아니다.
- `js/*.js`와 `server/*.mjs` 23개 파일의 Node 문법 검사 통과.
- 기존 버전별 정적 검사에는 최초 검토 때부터 오래된 화면 문자열을 요구하는 실패가 있었다. 이번 검증 결과가 그 검사 전체 통과를 뜻하지 않는다.

재현: Playwright 설치 후 저장소 루트에서 `python -m http.server 9154`를 실행하고 다른 터미널에서 `npm run test:entry`를 실행한다. 별도 Chromium은 `PLATE_BROWSER`, 주소는 `PLATE_TEST_URL`로 지정한다. 기본 스크린샷 출력은 `/tmp/plate-ui`다.

## 배포 전 확인

1. 별도 테스트 Firebase 프로젝트에서 본인의 입맛 읽기·저장, 다른 UID 접근 거부, 잘못된 필드 거부를 실제 규칙으로 검증한다.
2. Firestore 규칙과 신규 입맛 삭제를 포함한 탈퇴 서버를 먼저 배포하고, 이후 웹을 배포한다. 기존 규칙으로 웹만 배포하면 입맛 조회·저장이 거부되어 진입이 막힌다.
3. 실제 이메일/Google/Apple 로그인, 모바일 리다이렉트 복귀, 새 계정 저장·재로그인·탈퇴를 확인한다.

현재 변경은 웹 구현이다. 모바일 기술 선택과 푸시 알림은 후속 범위다. 푸시 구현 시 사용자가 설정한 식사 시간·시간대, 알림 수신/해제, 중복 방지, 알림 탭 시 해당 화면 복귀를 제품 요구사항으로 삼는다.

최초 검토에서 발견한 피드 게시 권한·좋아요 카운터·하위 댓글 권한 및 삭제·기존 탈퇴 오류 처리·주변 검색 거리 정렬 등은 별도 수정이 필요하다. 이 변경만으로 전체 서비스의 운영 준비가 완료된 것은 아니다.
