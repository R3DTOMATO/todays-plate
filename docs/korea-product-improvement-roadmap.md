# Today's Plate 한국 시장 추가 수정 로드맵

## 목표

한국의 대학생·직장인·1인 가구가 “오늘 뭐 먹지?”라는 고민을 짧게 끝내고 실제 식사 행동으로 이동하게 만드는 것을 우선합니다.

핵심 제품 지표는 **주간 활성 사용자당 완료된 식사 결정 수**입니다.

---

## P0 — 공개 테스트 전에 반드시 수정

### 1. 카카오 API를 서버 프록시로 이전

현재 프런트에서 직접 장소 API를 호출하는 구조는 키 노출과 호출량 통제가 어렵습니다.

필요 작업:

- Cloud Functions 또는 별도 Node 서버 구축
- API 키를 서버 환경변수로 관리
- IP·사용자별 호출 제한
- 동일 검색 결과 캐시
- 장애 시 카카오맵 직접 검색 링크 제공

### 2. 로그인과 데이터 동기화 구현

현재 핵심 데이터가 `localStorage` 중심이라 기기 변경·삭제 시 사라집니다.

필요 작업:

- Firebase Auth
- Firestore 사용자 프로필
- 찜, 식사 기록, 추천 피드백 동기화
- 계정 삭제 및 데이터 삭제 기능
- 비로그인 사용자의 익명 체험 후 계정 전환

### 3. 추천 이벤트 분석 추가

화면 조회만으로는 추천이 실제 식사로 이어졌는지 알 수 없습니다.

필수 이벤트:

- `recommendation_started`
- `recommendation_completed`
- `menu_shown`
- `menu_selected`
- `menu_rejected`
- `recipe_opened`
- `nearby_opened`
- `meal_recorded`
- `favorite_added`

이벤트에는 메뉴 ID, 시간대, 선택 조건, 후보 수, 추천 순위를 포함하되 알레르기 같은 민감 정보는 원문으로 저장하지 않습니다.

### 4. 알레르기와 일반 불호를 분리

알레르기는 추천 점수 감점이 아니라 강제 제외 조건이어야 합니다.

필요 작업:

- 알레르기·종교·비건 조건: 하드 필터
- 선호·불호·최근 먹음: 소프트 점수
- 교차 오염을 보장하지 않는다는 안내
- 메뉴 데이터에 주요 알레르기 유발 성분 필드 추가

### 5. 메뉴별 이미지와 데이터 품질 확보

현재 v2 사진은 음식 분류별 대표 이미지이므로 서로 다른 메뉴가 같은 사진으로 보일 수 있습니다.

필요 작업:

- 우선 사용 빈도가 높은 메뉴 50개 사진 확보
- 사진 비율 4:3 또는 1:1 통일
- 메뉴명, 가격, 열량, 조리 시간 검수
- 사진 출처·라이선스 기록
- 자체 CDN 또는 Firebase Storage 사용

### 6. 개발 도구를 사용자 빌드에서 분리

추천 검증과 레시피 QA 화면은 내비게이션에서는 숨겨졌지만 코드에는 포함되어 있습니다.

필요 작업:

- `/admin` 또는 별도 내부 프로젝트로 분리
- 운영 빌드에서 QA 코드 제외
- 관리자 인증 적용

## P1 — 한국 베타 리텐션 개선

### 1. 질문을 한국의 실제 식사 방식에 맞게 변경

현재 `간단 · 요리 · 외식` 분류는 사용자의 행동을 충분히 구분하지 못합니다.

권장 선택지:

- 집밥
- 외식
- 배달
- 편의점
- 아무거나

추가 조건:

- 혼밥 / 친구 / 연인 / 가족
- 10분 안 / 30분 안 / 시간 상관없음
- 5천 원 이하 / 8천 원 이하 / 1만 2천 원 이하 / 상관없음

### 2. 적응형 30초 추천

첫 사용자는 5~7개 질문을 받을 수 있지만, 재사용자는 저장된 취향을 활용해 1~3개만 묻습니다.

예시:

1. 집에서 먹을지 밖에서 먹을지
2. 가볍게 먹을지 든든하게 먹을지
3. 오늘 피하고 싶은 메뉴가 있는지

### 3. 추천 거절 이유 수집

`다른 메뉴`만 누르면 학습 신호가 불명확합니다.

권장 거절 사유:

- 오늘 당기지 않음
- 최근에 먹음
- 너무 비쌈
- 주변에 없음
- 조리하기 어려움
- 재료가 싫음

### 4. 주변 식당 결과 품질 개선

거리순만으로는 식사 결정에 충분하지 않습니다.

결과 카드에 필요한 정보:

- 현재 영업 여부
- 예상 거리와 도보 시간
- 가격대
- 대표 메뉴
- 카카오맵 평점·리뷰 수가 제공될 경우 함께 표시
- 배달 가능 여부는 별도 공급자 연동 시 표시

### 5. 한국형 메뉴 카테고리 보강

한국 사용자의 일상 선택을 반영해야 합니다.

우선 보강 영역:

- 편의점 조합
- 분식
- 국밥·찌개·백반
- 회사·대학가 점심
- 야식
- 해장
- 다이어트 도시락
- 배달 대표 메뉴

### 6. 온보딩 지연

첫 실행부터 많은 취향을 요구하지 말고 한 번 추천을 경험한 뒤 저장을 제안합니다.

권장 흐름:

`바로 추천 → 메뉴 선택 → “다음에는 더 잘 맞춰드릴까요?” → 취향 저장`

## P2 — 제품 확장과 수익화 준비

### 1. 같이 고르기

링크를 공유해 각자의 예산·불호·음식 종류를 모으고 공통 후보를 추천합니다. 커플, 친구, 동아리, 팀 점심에 적합합니다.

### 2. 대학가·오피스 상권 팩

초기에는 전국을 동일하게 다루지 말고 상권 단위로 추천 품질을 높입니다.

예시:

- 광운대 주변 8천 원 이하 점심
- 강남역 직장인 30분 점심
- 홍대 2인 저녁

### 3. 주간 리포트

건강 진단처럼 표현하지 않고 행동 기록으로 제공합니다.

예시:

- 이번 주 가장 자주 고른 음식 종류
- 평균 한 끼 예산
- 반복해서 선택한 메뉴
- 다음 주에 새로 시도할 메뉴

### 4. 웹 구조 현대화

현재 정적 HTML·대형 JavaScript 파일은 기능 확장 시 충돌 가능성이 큽니다.

권장 순서:

1. 추천 엔진을 순수 함수 모듈로 분리
2. 데이터 타입을 TypeScript로 정의
3. 화면을 React 또는 Expo로 이전
4. 공통 패키지와 모바일 앱 분리
5. 테스트 코드 추가

### 5. 구독은 리텐션 검증 후 도입

추천 횟수 제한보다 다음 기능을 유료화하는 편이 적합합니다.

- 커플·가족 프로필
- 장기 식사 통계
- 여러 명 조건 결합
- 냉장고 재료 추천
- 광고 제거

## 한국 베타 통과 기준

다음 수치는 업계 평균이 아니라 내부 의사결정을 위한 목표입니다.

- 추천 완료율 70% 이상
- 후보 3개 안에서 메뉴 선택률 50% 이상
- 추천 후 레시피·식당·기록 행동률 35% 이상
- 사용자당 주간 완료된 식사 결정 3회 이상
- D7 유지율 25% 이상
- 추천 결과 없음 비율 5% 미만
