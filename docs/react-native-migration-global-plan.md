# Today's Plate — React Native 마이그레이션 & 글로벌 배포 계획

> 기준 커밋: `todays-plate` main 브랜치 v5.0.0 (Figma Award UI/UX)
> 작성일: 2026-08-28

## 0. 이 문서의 목적

기존 정적 웹 베타(`index.html` + `js/app.js`)를 React Native(Expo) 앱으로 전환하고,
**한국 전용 베타에서 글로벌 서비스로 확장**하기 위한 실행 순서를 정리합니다.
웹 배포 체크리스트(`docs/korea-deployment-checklist.md`, `docs/korea-product-improvement-roadmap.md`)의
P0 작업과 겹치는 부분은 중복 진행하지 않고 순서를 조정했습니다.

---

## 1. 왜 React Native인가 (Flutter 대비)

- 핵심 비즈니스 로직(추천 엔진, 알레르기 하드필터, 최근 3일 메뉴 반복 차단, 예산 계산)이 전부
  `js/app.js` 안의 JavaScript로 구현되어 있음
- 기존 회귀 테스트(`scripts/validate-recommendation-*.mjs`)를 순수 함수 단위로 그대로 재사용 가능
- Flutter로 가면 위 로직 전체를 Dart로 재작성해야 하며, 그 과정에서 검증된 추천 규칙이
  깨질 위험이 큼
- `server/kakao-nearby-proxy.mjs` (Railway 백엔드)는 RN에서도 그대로 API 서버로 재사용 가능

## 2. 로컬(한국) 기준 마이그레이션 단계

### 2.1 추천 엔진 순수 함수 분리
- `app.js`에서 DOM 조작과 섞여 있는 추천 로직을 `recommendMenu(input, state)` 형태의
  순수 함수로 분리
- 기존 `validate-recommendation-v4.4~v5.0.mjs` 테스트를 이 함수 기준으로 재실행 가능하도록 조정
- 이 단계가 끝나야 RN/웹 양쪽에서 같은 추천 엔진을 공유할 수 있음

### 2.2 데이터 레이어 이식
- `data/menus.json`, `data/recipes.json`, `data/dining-guides.json`,
  `data/restaurant-keywords.json`을 포맷 변경 없이 RN 프로젝트에 번들
- 단, 아래 3번(글로벌 확장) 작업과 맞물려 **스키마에 `locale`/`country` 필드 추가** 필요

### 2.3 TypeScript 타입 도입
- 메뉴, 레시피, 사용자 프로필, 이벤트 스키마를 타입으로 정의
- `docs/firebase-schema.md`에 정의된 Firestore 구조를 타입 소스로 사용

### 2.4 Expo 프로젝트 스캐폴딩
- 기존 12개 Figma 화면(홈/결과/탐색/주변식당/레시피/그룹투표/식사기록/내입맛/로딩/빈상태/오류 등)을
  화면 단위 컴포넌트로 매핑
- 네비게이션은 React Navigation (탭: 홈/탐색/찜/기록/프로필)

### 2.5 네이티브 기능 강화
- 위치 권한 (expo-location)
- 카메라/사진 (expo-image-picker) — 식사 기록 사진을 현재 웹의 1280px 압축 로직 그대로 이식
- 푸시 알림 (expo-notifications) — 현재 웹 버전에는 없는 기능, P2 로드맵 항목이었으나 RN 전환 시 자연스럽게 추가

### 2.6 Firebase Auth + Firestore 동기화
- 웹 P0 체크리스트의 미해결 항목이었던 Auth/Firestore를, 웹에서 먼저 검증한 뒤
  RN에는 검증된 스키마 그대로 이식 (순서 중요 — 4번 참고)

### 2.7 백엔드 유지
- `server/kakao-nearby-proxy.mjs`(Railway)는 한국 서비스용으로 유지
- 글로벌 서비스는 별도 프록시 서버 추가 (3.2 참고)

## 3. 글로벌 배포를 위한 추가 작업

웹 베타는 철저히 **한국 시장 전제**로 설계되어 있습니다. 글로벌 확장 시 다음 부분은
"이식"이 아니라 "재설계"가 필요합니다.

### 3.1 지도/장소 검색 API 교체 — 최우선 이슈
- **Kakao 로컬 API는 한국 밖에서 사용 불가**
- 글로벌 버전은 Google Places API(또는 국가별 병행: 일본 Yahoo!, 미국/유럽은 Google 단일)로 교체
- `server/kakao-nearby-proxy.mjs` 구조를 참고해 `places-proxy` 서버를 국가/제공자별로 라우팅하는
  형태로 재설계 (예: `country=KR` → Kakao, 그 외 → Google Places)
- API 키/쿼터/과금 체계가 Kakao와 Google이 다르므로 요금 정책 재검토 필요

### 3.2 메뉴·추천 로직의 문화적 편향 제거
- 현재 로직은 "한국 사용자에게는 한식을 대표 메뉴로 우선"(v4.7) 등 한국 특화 규칙이 하드코딩됨
- 글로벌 버전은:
  - 국가/지역별 기본 음식 문화 데이터셋 필요 (한국 197개 메뉴 → 국가별 메뉴 DB 별도 구축)
  - "집밥 대표 메뉴는 사용자 국가 기준"(v4.5 변경사항)이라는 원칙 자체는 이미 국가 확장을 염두에 둔 설계이므로 재사용 가능하나, 실제 국가별 데이터가 없음 → 데이터 구축이 가장 큰 작업
  - 예산 단위(원 → USD/EUR/JPY 등)와 구간(1만원/3만원/5만원)도 국가별 물가에 맞게 재산정

### 3.3 다국어(i18n) 아키텍처
- 현재 UI 문자열이 `index.html`/`app.js`에 하드코딩된 한국어 → i18n 라이브러리(i18next 등)로 전면 분리
- 레시피 설명문(`data/recipes.json`)도 언어별 재작성 필요 — 기계번역이 아닌 현지화 권장
  (레시피 저작권 정책 `docs/recipe-copyright-policy.md`의 "출처 재작성" 원칙을 언어별로 다시 적용)

### 3.4 법적/규제 대응
- 개인정보: 한국 개인정보보호법(PIPA) 대응 문서 외에 **GDPR(EU), CCPA(미국 캘리포니아)** 등
  진출 국가별 별도 대응 필요 — 동의 방식(옵트인/옵트아웃)이 지역마다 다름
- 위치 정보 처리 고지 문구도 지역별 법규에 맞게 재작성
- 앱스토어 심사 가이드라인 차이 (예: 미성년자 데이터 처리, 알레르기 정보 같은 건강 관련 고지 요건)

### 3.5 인프라
- Railway 단일 리전 배포 → 지연시간을 고려해 지역별 리전 분리 또는 CDN 앞단 구성 검토
- Firebase 프로젝트도 데이터 거주(data residency) 요건이 있는 지역(EU 등)은 별도 리전 설정 필요

### 3.6 이미지/에셋
- Unsplash 임시 이미지를 라이선스 이미지로 교체하는 작업(P0)을 이번에 글로벌 음식 이미지까지
  한 번에 확보하는 것이 효율적 (한국만 먼저 하고 나중에 다시 안 하도록)

## 4. 통합 실행 순서 (권장)

한국 P0 검증 → RN 전환 → 글로벌 확장 순으로, 리스크를 낮추는 순서입니다.

1. 추천 엔진 순수 함수 분리 (2.1)
2. 웹 버전에서 Firebase Auth/Firestore 먼저 검증 (한국 P0)
3. 분석 이벤트 실제 플랫폼 연동 + 크래시 모니터링 (한국 P0)
4. 광운대·노원 비공개 베타 50명 (한국 P1) — 여기서 RN 전환과 병행 가능
5. Expo 스캐폴딩 + 화면 이식 (2.2~2.5)
6. 검증된 Auth/Firestore 스키마를 RN에 이식 (2.6)
7. **Google Places API 프록시 구축** (3.1) — 글로벌 확장의 최우선 기술 작업
8. 국가별 메뉴 데이터셋 1개국 우선 구축 (예: 일본 또는 미국 중 하나를 파일럿으로) (3.2)
9. i18n 아키텍처 도입, 해당 1개국 언어로 우선 적용 (3.3)
10. 해당 국가 법적 문서/스토어 심사 대응 (3.4)
11. 파일럿 국가 출시 → 지표 검증 → 국가 추가 확장

**중요:** 한 번에 모든 국가를 동시에 준비하지 말고, 위 7~11번을 "국가 1개 파일럿" 단위로
반복하는 구조를 권장합니다. 메뉴 데이터·법적 문서·번역 품질 모두 국가마다 검증 비용이 크기 때문에,
검증된 국가 1개를 먼저 성공시킨 뒤 같은 패턴을 반복하는 편이 안전합니다.

## 5. 자체 주문/배달 시스템 (사업 성격 전환)

> **중요:** 이 섹션부터는 "메뉴 추천 앱"이 아니라 "배달 플랫폼 사업"으로 성격이 바뀝니다.
> 기술 로드맵이 아니라 별도 사업 계획으로 다뤄야 할 항목이 많습니다.

### 5.1 조사 결과 요약 (2026년 8월 기준)
- 배민·쿠팡이츠·요기요 자체에는 외부 앱이 주문을 넣을 수 있는 오픈 API가 없음 (그대로는 우회 불가)
- **다만 배달대행사(바로고/부릉/생각대로/스파이더 등) 쪽은 실제로 API 연동이 열려있음** —
  요기요도 2024년 11월부터 바로고와 "가게배달 주문 연동"을 시작했고, 여러 개발사가
  "배민과 유사한 자체 배달앱 + 배달대행사 API 연동" 구조로 실제 서비스를 운영 중
- 즉, **주문을 받고 나서 라이더를 부르는 마지막 구간은 기술적으로 막혀있지 않음**
- 막혀있는 건 그 앞단 — 가맹점 확보, 결제, 법적 요건, 운영

### 5.2 필요 구성 요소

| 구성 요소 | 내용 | 난이도 |
|---|---|---|
| 가맹점 관리 시스템 | 식당이 메뉴·가격·영업시간·품절 상태를 등록/수정하는 관리자 화면(웹 또는 태블릿 앱) | 개발 자체는 중간, **영업(가맹점 유치)이 진짜 난관** |
| PG 결제 연동 | 토스페이먼츠/이니시스 등과 가맹점 계약, 카드결제 API 연동 | 중간 (표준화된 SDK 존재) |
| 배달대행사 API 연동 | 바로고/부릉/생각대로 중 하나 이상과 계약 후 주문 생성 시 자동 배차 요청 | 낮음~중간 (확인된 선례 다수) |
| 정산 시스템 | 가맹점별 매출 집계, 수수료 차감, 정산 주기(주/월) 관리 | 중간 |
| 주문 상태 실시간 추적 | 접수→조리중→배달중→완료 상태를 앱에서 실시간 표시 | 중간 (웹소켓/FCM) |
| CS/환불 프로세스 | 주문 취소, 오배달, 품절 대응 인력·프로세스 | 개발 아님 — **운영 인력 필요** |
| 법적 요건 | 통신판매업 신고, 전자상거래법 준수, PG사 심사, 개인정보보호(결제정보) | 법무 검토 필요 |

### 5.3 권장 실행 순서 (MVP 우선)

**Step 1 — 파일럿 지역·가맹점 소규모 확보**
- 처음부터 전국 단위가 아니라 **1개 대학가/동네, 가맹점 10~20곳** 규모로 직접 영업
- 광운대·노원 P1 베타 지역과 겹치면 효율적 (이미 검증 중인 사용자 기반과 결합 가능)

**Step 2 — 결제 + 배달대행사 API 최소 연동**
- 토스페이먼츠(간편결제) + 바로고 또는 부릉 중 1곳과 우선 연동
- 이 단계에서 자체 라이더는 두지 않고 100% 배달대행사에 위탁

**Step 3 — 가맹점 관리 도구**
- 처음엔 정교한 태블릿 POS 대신, 식당 사장님용 간단한 웹 대시보드(주문 접수/거절, 메뉴 온오프)로 시작

**Step 4 — 운영 프로세스 확립**
- 주문 취소율, 배차 지연, CS 응대 시간 등을 소규모로 먼저 검증한 뒤 지역 확장

**Step 5 — 법적/정산 체계 정식화**
- 파일럿 단계를 넘어 실제 매출이 발생하는 시점에 통신판매업 신고, 정산 자동화, 법무 검토 완료

### 5.4 RN 마이그레이션과의 관계
- 자체 주문 기능은 **Firebase Auth/Firestore 연동(2.6) 이후에 얹는 게 안전** — 주문 내역은 익명 사용자로 처리할 수 없고 반드시 인증된 계정과 연결되어야 함
- 가맹점 관리 시스템은 소비자용 RN 앱과 별도로 **웹 기반 관리자 대시보드**로 분리 개발하는 것을 권장 (React 웹 그대로 재사용 가능, RN으로 만들 필요 없음)

### 5.5 솔직한 리스크 평가
가맹점 확보와 운영 인력 없이는 아무리 API 연동이 잘 되어 있어도 자체 주문 시스템은 작동하지 않습니다.
배민·쿠팡이츠가 수천억 원의 마케팅/영업비를 투입한 부분이 바로 이 지점입니다.
**소규모 파일럿(Step 1~2)으로 실제 주문 전환율·가맹점 만족도를 먼저 검증한 뒤,
그 결과를 보고 전면 투자 여부를 결정하는 것을 권장합니다.**
